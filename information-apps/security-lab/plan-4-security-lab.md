# 実装計画④「情報セキュリティ体験」

## 1. 概要
- **対象**: 技術分野 D「情報の技術」(情報セキュリティ、情報モラル、ネットワークと情報の利用、安全・適切な利用)
- **ねらい**: 「脅威→仕組み→対策」を、実際に手を動かして体験し、なぜその対策が必要かを自分の言葉で説明できるようにする。
- **安全設計**: すべてブラウザ内の疑似環境で完結。実在のネットワーク・サイトには一切接続せず、攻撃を実行するツールは含まない(体験は教育用の模擬)。

## 2. 学習目標
1. パスワードの強度と攻撃への耐性の関係を理解する。
2. 暗号(共通鍵・公開鍵)の考え方と必要性を理解する。
3. フィッシング、マルウェア、SNSの個人情報流出などの危険に気付き、判断できる。
4. 個人情報、著作権、デジタルタトゥーについて、適切な行動を選べる。

## 3. モジュール構成(ミニ教材の集合)
| # | モジュール | 内容 |
|---|---|---|
| 1 | **パスワード強度ラボ** | 入力(練習用のダミー文字列を推奨)した文字列の「推定解読時間」を表示。文字種・長さを変えると桁違いに変わるグラフ。パスフレーズの利点。※入力は端末外に送られない旨を明示 |
| 2 | **暗号ラボ** | シーザー暗号(ずらし)→ 頻度分析で解読→ ビジェネル暗号→ 鍵の受け渡し問題→ 公開鍵暗号(小さな素数でRSA体験) |
| 3 | **ハッシュ体験** | 文字を少し変えるとハッシュが全く変わる様子。ファイル改ざん検出の考え方 |
| 4 | **フィッシング見分け** | 擬似メール/擬似ログイン画面を見て「怪しい点」をタップ(URL、差出人、急かす文面、不自然な日本語)。解説付き |
| 5 | **ネットワーク通信の模擬** | 「平文HTTP」vs「HTTPS」で、途中の覗き見(盗聴者)に何が見えるかをアニメで比較 |
| 6 | **SNS投稿の個人情報チェック** | 写真・文章から「位置・学校・日常」が特定できる要素を探す(位置情報、制服、背景の看板、影の向き) |
| 7 | **デジタルタトゥー/拡散シミュレーション** | 投稿が共有されて広がるアニメ。削除しても残る理由を体験 |
| 8 | **著作権・利用ルールクイズ** | 引用・私的利用・フリー素材の分岐クイズ |
| 9 | **判断ロールプレイ** | 分岐型ストーリー(知らない人からのDM、無料アプリの権限要求、友達のパスワード) |
| 10 | **まとめ・行動宣言** | 学んだ対策から「自分が今日から実行する3つ」を選択・記録 |

## 4. 機能要件
### MVP(モジュール1・2・4)
- 共通UI(章ナビ、進捗、解説カード、ふりかえり)。
- 端末内に進捗とふりかえり記録を保存、教員向けの集計用JSON/CSVエクスポート。
### 第2段階
- モジュール3・5・6。
- 理解度チェック(選択式)と間違い箇所の復習。
### 第3段階
- モジュール7〜10、教員用に問題データを差し替えられる設定ファイル。
- 簡易の多言語対応(やさしい日本語/ルビ)。

## 5. 技術設計
- **構成**: PWA、Vanilla JS(モジュールごとにESモジュール)、`modules/*.js`、`data/*.json`(問題・シナリオ)。
- **暗号・ハッシュ**: Web Crypto API(SHA-256)。RSA体験は教育用の小さな数をBigIntで実装(実運用の鍵長ではないことを明記)。
- **解読時間推定**: 文字種数^長さ ÷ 仮定の試行速度(例: 10^10回/秒。仮定を画面に明示し変更可能)。「よくあるパスワード辞書」は小さなリストを同梱(上位数百語)。
- **パスワードの扱い**: 入力値は保存しない・送信しない(メモリ内のみ)。画面で「実際のパスワードは入力しないで」と注意。
- **フィッシング素材**: 架空のドメイン/ロゴ風画像で作成(実在企業のロゴ・名称は使わない)。
- **アクセシビリティ**: キーボード操作、色に頼らない表示、読み上げ対応のaria。

## 6. 教育設計上の工夫
- **「怖がらせる」のではなく「判断の手順」を持たせる**: 「立ち止まる→確認する→相談する」の3ステップを各モジュールで反復。
- **ふりかえり**: 「なぜその対策が有効か」を一言で書かせる(用語の暗記で終わらせない)。
- **授業案との組み合わせ**: 1モジュール10〜15分、導入/まとめで使えるようにする。

## 7. 開発スケジュール目安
| 週 | 内容 |
|---|---|
| 1 | 共通UI、進捗保存、モジュール1(パスワード) |
| 2 | モジュール2(暗号: シーザー〜頻度分析〜RSA) |
| 3 | モジュール4(フィッシング)+データ形式の確立 |
| 4 | モジュール3・5、理解度チェック、実機テスト |
| (5〜) | モジュール6〜10、教員向け設定 |

## 8. テスト・受け入れ基準
- オフラインで全モジュールが動作、外部リソースへのリクエストが0件(DevToolsで確認)。
- 暗号処理の正しさ(既知ベクタのユニットテスト)。
- 入力したパスワードが保存・ログ・エクスポートに含まれないことを確認。
- 生徒の理解テスト(事前・事後の小テスト)で正答率が向上すること。

## 9. リスクと対策
| リスク | 対策 |
|---|---|
| 攻撃手法の教授になってしまう | 実行可能な攻撃ツールは作らず、概念のモデル(アニメ・小規模計算)に限定 |
| 実際のパスワード入力 | 注意表示、ダミー例の提示、保存しない設計 |
| 情報が古くなる | データ(辞書・シナリオ・脅威の例)を `data/` に分離し更新しやすく |
| 一度やって終わりになる | 学期を通じた短いクイズ・事例アップデート機能 |

## 10. 拡張アイディア
- 校内ルール(スマホ・SNS利用)の作成ワークシート(生徒が主体的にルールを提案)
- 保護者向けの1枚資料の自動生成(学んだ内容の要約)

## 付録: 学習指導要領(平成29年告示)本文との照合
- 技術分野 D ⑴ア「情報の表現、記録、計算、通信の特性等の原理・法則と、**情報のデジタル化や処理の自動化、システム化、情報セキュリティ**、情報モラルの必要性」。内容の取扱い(4)ア「**情報のデジタル化の方法と情報の量**、著作権を含む**知的財産権**、**発信した情報に対する責任**、社会における**サイバーセキュリティ**」。
- 本計画の不足: 「**情報のデジタル化と情報量**」(画像の解像度・階調、音の標本化、圧縮によるデータ量変化)を扱うモジュールが無い → **モジュール11として追加**する。
- 「発信した情報に対する責任」→ モジュール7(拡散)・8(著作権)に「発信者としての責任」の設問を明示する。
- (4)イ「個人情報の保護の必要性」(⑵コンテンツ関連) → モジュール6に対応済み。
- 「サイバーセキュリティ」→ モジュール4・5を「サイバーセキュリティ」の語で整理する。
- ⑶「計測・制御のプログラミング」「⑵双方向性のあるコンテンツ」は本アプリの対象外。ビジュアルプログラミング環境(別アプリ)で扱う。
