## 全体の印象

- 作り込みはていねい。タッチ領域はすべて44px以上で、横スクロールなし、コンソールエラー0件。再読み込みしても状態が戻る(タブ・栽培・操作・振り返り)。iframe 埋め込みでも同じように動く。confirm/alert/prompt は使っておらず、モーダルも5サイズすべてで画面内に収まる。
- 一方で、学習の中心である「原因さがし」に問題がある。最善に近い育て方をしても、天気(くもり・雨)による「光不足」が毎回いちばんの原因と判定される。そのため生徒は、自分では変えられない原因を「正解」として覚えてしまう。

- ほかの教材(B1・B3・B4)には「文字を大きく」と kzConfirm(危険操作は赤ボタン)があるが、B2 にはない。教材集の中で操作がそろっていない。

### B2-01 原因さがしの「正解」が、ほぼ毎回 天気による「光が足りない」になる
- 重要度: **高** / 観点: 内容の適切さ・難易度
- 場所: ③結果・原因さがし。`analyze()` L726-752(特に L732 と L747)、`step()` の limit 判定 L655-656、光の台形関数 L583・L587、作物の light 値 L492-509、WEATHER L532-536、ヒント L1308・L1314-1324、クイズ L1325-1341
- 何が問題か: ミニトマトの光の「ちょうどよい」は 70以上だが、くもりの日の光は 65、雨の日は 40 になる。このため、天気だけで毎日のように「光が足りない」と判定され、損失として積み上がっていく。上手に育てて○になった生徒がクイズで「水」や「温度」を選ぶと、「❌おしい! いちばん影響が大きかったのは『光が足りない』ことでした」と言われる。ところが、光を強くする操作はゲームの中にない。ヒントにも「くもり・雨の日の光不足は人の手では変えにくい」と書かれている。生徒は「何を直せばよかったのか」がわからない。さらに、ゲージは毎日「光 足りない▼」と青字で警告するのに、打つ手がない。
- 根拠:
  - 画面操作で慎重にプレイ(毎日ゲージを見て温度・水・肥料を調節し、病気が出たら見回り)→ ○・実12個 → 正解は「光」(`shots/b2/06_result_good_quiz_full.png`)
  - モデルを直接まわした結果(sim.js): 全48通り(作物×環境×季節)を、1日ごとに最善の操作を選ぶ方法でプレイすると、ほぼすべてで main=L/low になった。「大きな失敗はありませんでした」(L1322)は事実上出ない。
- 具体的な直し方:
  1. `analyze()` で光の損失を2つに分ける。遮光による分 `f.L(遮光あり) と f.L(遮光なし) の差` だけを「操作による光不足」として `loss.L` に入れる。天気による分は `loss.weather` として別に記録する。
  2. main の判定は loss.T / L / W / N(操作で変えられる分)だけで行う。全部が閾値(例 2.0日分)より小さければ main=null にする。
  3. main=null のときは、クイズに5つ目の選択肢「🌤 どれも大きな問題なし(天気のせい)」を出し、それを正解にする。
  4. ゲージの光は、遮光していない日は「天気で弱い(変えられない)」と灰色の文字で表示し、赤や青の警告にしない。
  5. ヒント L_low は、遮光した日が2日以上あったときだけ出す。くもり・雨だけのときは「天気のせいで光が弱い日がn日。場所えらび(日当たり)が大切」という情報ヒントに分けて、件数の並び順で先頭に来ないようにする。

### B2-02 そだてる画面で「操作ボタン」と「予想ゲージ」「その日の結果」を同時に見られない
- 重要度: **高** / 観点: 操作のわかりやすさ・UI
- 場所: ②そだてる。レイアウト L72・L188-192・L292-331、`advance()` L1270-1284(ボタンを押してもスクロール位置が変わらない)
- 何が問題か:
  - 縦向き(800x1280 と 800x1224)は1列表示で、植物の絵・観察メモ → 天気・ゲージ → 操作 の順に並ぶ。操作の位置までスクロールして「次の日へ」を押すと、観察メモは画面の外(top=-62px)、植物の絵も外(-426px)にある。何が起きたか(しおれた、花がさいた、病気、など)が目に入らないまま、次の日の操作を始めてしまう(`shots/b2/10_p_grow_day3_afterNext.png`)。
  - 横向き(1280x800 と 1280x744)は2列表示。水やり・肥料・見回りのボタンを見ようと下へスクロールすると、天気予報と予想ゲージが画面上端の外(top=-204px)に出る。画面の「操作を変えると予想も変わる」という仕組みが見えなくなる(`shots/b2/04_good_day10.png`)。
- 根拠: t3.js の計測値 `p after next visibility {"memoTop":-62,"plantTop":-426,...}` と `li {"gaugeTop":-204,...}`
- 具体的な直し方:
  1. 各操作グループの見出しの右に、その条件の予想値を小さなチップで出す。例: `💧 水やり 予想 68% ちょうどよい○`。`opGroup()` に `c.dir` と値を渡せばよい。こうすればゲージが見えなくても判断できる。
  2. 「次の日へ」を押したあとにトーストで「◯日目: (観察メモの1文目)」を2.5秒表示する。悪いバッジ(bad)が出た日は、`#b2-memo` まで `scrollIntoView({block:'center'})` する。
  3. 縦向き(max-width:900px)では並び順を「天気 → ゲージ → 操作 → 植物・メモ・グラフ」に変える(`.b2-grow > div:first-child{order:2}`)か、植物・バッジ・観察メモを1行に縮めた要約バーを `.b2-actions` のすぐ上に置く。

### B2-03 最初の画面では、操作バー(次の日へ)が「光」以降の操作をかくしている
- 重要度: 中 / 観点: 操作のわかりやすさ
- 場所: ②そだてる `.b2-actions{position:sticky;bottom:0}` L116、L320-324
- 何が問題か: 1280x800 でスクロールしていない状態だと、操作カードの中で見えるのは「🌡 温度」だけ。その下の「光・水やり・肥料・見回り」は、画面下に貼り付いた操作バーの裏にかくれている(`shots/b2/03_grow_day0_1280x800.png`)。生徒は、オレンジの大きな「次の日へ ▶」だけを押し続けやすい。実際、何もしないで進めると25日目にかれる(sim2.js の nothing → ✕・dead)。
- 具体的な直し方: 0日目と、ほかの操作に一度も触れていないときは、「次の日へ」の上に「⬇ 水やり・肥料・見回りもえらぼう」という1行の案内を出す。あるいは `.b2-actions` を sticky にするのは `#b2-ops` がビューポートに入ったときだけにする(IntersectionObserver でクラスを切り替える)。B2-02 のチップと組み合わせるとよい。

### B2-04 雨が1日ふっただけで「茎がひょろ長く(徒長)」と出る。バッジ「😊元気」とも食い違う
- 重要度: 中 / 観点: 内容の適切さ
- 場所: `step()` 徒長の判定 L632-638、観察メモ L1126、バッジ L1103(stretchDays を通算で数えている)、ヒント L1321
- 何が問題か: 光の係数が 0.55 未満なら、その日のうちに徒長と判定される。ミニトマトでは雨の日(光40)ごとに必ずそうなる。1日目が雨だと、観察メモは「茎が細くひょろ長くのびている。光が足りないのかも?」なのに、バッジは「😊 元気」になる(`shots/b2/80_grow_1280x600_scrolled.png`)。実際の徒長は、日照不足・高温・多湿や窒素過多が何日も続いて起こるもの。1日で起きると覚えさせるのは誤解のもと。さらに、日なたで最善に育てても「徒長が6〜7日」とヒントに出る(sim2.js POL tomato sun: stretch=7)。
- 具体的な直し方: 連続日数 `stretchRun` を持ち、光不足と温度条件が3日以上続いたときだけ徒長と判定する(`stretch = stretchRun >= 3`)。メモ・バッジ・ヒントは、すべてこの同じ判定を使う。バッジの条件も通算の stretchDays ではなく stretchRun で見る。

### B2-05 ヒントの「〜日ありました」と、グラフの緑の帯の外にある日数が合わない
- 重要度: 中 / 観点: 内容の適切さ・難易度(グラフの読み取り)
- 場所: 日数の数え方 L734(`f<0.7` の日だけ数える)と、グラフの帯 L1392-1395(帯は「ちょうどよい範囲」b〜c)、クイズの文 L1331
- 何が問題か: クイズは「下のグラフで『ちょうどよい範囲』から外れた日を数えて予想しよう」と指示している。しかし光のグラフを見ると、帯の下にある日は13日以上あるのに、ヒントは「光が足りない日が7日」と言う(`shots/b2/06_result_good_quiz_full.png`)。言われたとおりに数えた生徒ほど混乱する。
- 具体的な直し方: 数える条件を、グラフと同じ `dir !== 'ok'`(帯の外)にそろえる。「大きく外れた日」を別に数えたいなら、グラフにもう1本、薄い赤の帯(f<0.7 の境目)を描き、ヒントにも「大きく外れた日」と書く。

### B2-06 ◎になれるかどうかが天気の番号しだい(番号1のミニトマトは、最善でも○)
- 重要度: 中 / 観点: 難易度
- 場所: `grade()` L711-719(◎は q≥0.72)
- 何が問題か: 1日ごとに最善の操作を探す方法(beam.js)で調べると、既定の「ミニトマト/露地/初夏/番号1」の最高は q=0.67 で○どまりだった。イネ/露地/初夏は番号1〜5のどれでも◎に届かない。ミニトマトの番号2・5やダイズは◎になる。先生がクラス全員に番号1を指定すると、「どうやっても◎がとれない」となり、くり返し試す意欲が下がる。
- 根拠: `beam.js` の出力 `tomato/field/early/1 best ○ q=0.67`、`rice/field/early/1〜5 best ○`
- 具体的な直し方: 評価を絶対値ではなく、その天気での最善値との比率にする。起動時に `simulatePolicy` の「理想ルール」(または同じ beam 探索)で q_best を求め、`q / q_best` が 0.9 以上なら◎とする。または B2-01 の対策で天気による光の損失を除いたうえで、閾値を作物ごとに調整する。結果画面に「この天気での最高の目安: 実の数◯個」を出すのもよい。

### B2-07 ダイズは14日目に開花、ミニトマトは30日以内に赤い実が多数。生育の時期が実際と大きくずれる
- 重要度: 中 / 観点: 内容の適切さ(先生による事実確認)
- 場所: CROPS.soy の reproStart:14(L504)、開花メモ L1132、トマトの実の描き方 L992-995
- 何が問題か: ダイズ(エダマメを含む)の開花は、早生品種でも種まきから30〜40日ごろ。種まきから14日目に「花がさいて、さやがつきはじめた!」とし、30日目に「さやの数18個」とするのは実際と合わない。ミニトマトも、開花から赤く熟すまで40〜50日ほどかかる。植えつけから30日以内に赤い実が4個中3個の割合で描かれるのは不自然。実物を育てて育成日誌(B1)とくらべると、すぐに矛盾が出る。
- 具体的な直し方:
  - ダイズは「つぼみ・花の数(個)」を指標にし、reproStart を 25 前後にする。あるいは表示名を「花芽の数」にする。開花メモも「つぼみができはじめた!」にする。
  - トマトは「ついた実の数」とし、実は緑色で描く(`fill` は常に '#8bc34a'、最終日だけ一部オレンジ)。
  - ①の注意書きに「30日は栽培の前半だけ」と1行加える。

### B2-09 「同じ操作で5日 ▶▶」で、追肥や水たっぷりも5日続けて行われる
- 重要度: 中 / 観点: 操作のわかりやすさ
- 場所: `advance()` L1270-1279、ボタン L323、説明文 L1242
- 何が問題か: 画面の説明は「水やり・肥料・見回りは毎日えらび直します」だが、5日送りでは同じ操作が5回くり返される。「たっぷり」を選んで押すと、5日目には根ぐされとアブラムシが出て、7日目にかれる(`shots/b2/20_water_lots_next5.png`、`20_water_lots_dead.png`)。追肥を選んで押すと、養分が+60になり肥料やけを起こす。生徒は「1回やるつもり」で押してしまう。
- 具体的な直し方: 5日送りでは、温度と光だけを5日続ける。水やり・肥料・見回りは1日目だけ反映し、2〜5日目は「やらない」にする(`advance` のループの中で i>0 のとき `a2 = {temp:a.temp, shade:a.shade, water:'none', fert:false, guard:a.guard}`)。今の動きを残すなら、水たっぷりや追肥が選ばれているときに「5日間 毎日たっぷり/追肥 します。いいですか?」と確認モーダル(ask)を出す。

### B2-11 くらべるの結果が、ボタンを押さなくても入れ替わったり、古いまま残ったりする
- 重要度: 中 / 観点: バグ・操作のわかりやすさ
- 場所: `renderCompare()` L1443(`if (c.last) drawCompareOut()`)、プリセット L1658-1663、change ハンドラ L1696-1703、resize L1728
- 何が問題か:
  - 結果を出したあとで B の水やりを変えると、結果は古いまま残る。
  - その状態でタブを行き来すると、くらべるボタンを押していないのに、新しい条件で計算し直した結果(B が8日目にかれた)に変わる。くらべた記録(cmphist)には残らない。
  - プリセットをタップしたときも、結果がだまって入れ替わる。
  - 作物をラディッシュに変えても、見出しは「ミニトマト」のまま。
  - 生徒は、どの条件の結果を見ているのかわからなくなる。振り返りの自動記録とも食い違う。
- 根拠: t6.js の出力 `result still says ... B✕ あまり育たなかった` → タブ移動後 `B✕ かれてしまった(8日目にかれた)`、`cmphist len 1`
- 具体的な直し方: くらべるボタンを押したときの条件のスナップショット `c.last = {at, crop, season, seed, A:{...}, B:{...}}` を保存する。`drawCompareOut()` は常にこのスナップショットで描く。条件を変えたら、結果カードを半透明にして「⚠ 条件が変わりました。『30日間育ててくらべる』をおして結果を更新しよう」と表示する。

### B2-12 くらべるのメモ欄で入力中に画面サイズが変わると、入力欄が作り直されてフォーカスが外れる
- 重要度: 中 / 観点: バグ(タブレットの実機では未確認、ほぼ確実)
- 場所: resize ハンドラ L1721-1730 → `drawCompareOut()` が `out.innerHTML` を作り直す(L1481)
- 何が問題か: Android タブレットでは、ソフトキーボードが出ると画面サイズが変わり resize イベントが起きる。そのたびに textarea が作り直され、フォーカスが外れてキーボードが閉じる。「気づいたこと」が書けなくなる。テストでは、入力中に viewport を 1280x500 へ変えたところ activeElement が body に移った(値は残った)。
- 具体的な直し方: resize のときはグラフ(canvas)だけを描き直す。描画部分を `drawCompareCharts(ra, rb)` として分け、resize からはそれだけを呼ぶ。textarea を含む HTML は作り直さない。

### B2-14 くらべるのグラフに「光」と「養分」がない
- 重要度: 中 / 観点: 内容の適切さ・グラフの読み取り
- 場所: `drawCompareOut()` L1478-1494(グラフは草丈・健康度・水分・温度の4つだけ)

### B2-15 プリセット「かわいたら水 と 水やりなし」で、ラディッシュ(春)は差が出ない
- 重要度: 中 / 観点: 内容の適切さ
- 場所: PRESETS L1417、環境 field の rain・evap(L516)

- 再読み込み: 栽培の日数・選んでいた操作・タブ・振り返り・ふりがなの設定がすべて戻る。入力から600ms以内に再読み込みしても、pagehide で保存されて消えない。
